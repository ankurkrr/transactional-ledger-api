## 1. Executive Summary & Purpose

This document establishes the functional and non-functional requirements extracted directly from the authoritative *Full Stack Developer Assessment* document. It categorizes requirements, defines a rigorous requirements traceability matrix, clarifies ambiguities, and sets engineering safeguards required for a financial-grade transactional ledger.

---

## 2. Categorization of Requirements

To avoid conflating stated assessment requirements with implementation assumptions, all statements are grouped into four categories:

1. **Explicit Requirements (ER):** Behaviors directly stated in the assessment PDF.
2. **Engineering Safeguards (ES):** Mandatory architectural, concurrency, and security controls needed to ensure correctness, financial invariants, and prevent exploitation.
3. **Assumptions Requiring Approval (AA):** Decisions where the assessment is silent or open to multiple standard interpretations.
4. **Optional Enhancements (OE):** Features explicitly labeled as bonus or optional by the assessment.

## 3. Explicit Requirements Extracted from Assessment

### 3.1 Account Creation (PDF Page 1, Section 1)
- **ER-ACC-01:** System must provide an API to create a new account.
- **ER-ACC-02:** Each account must contain:
  - `id`: Unique account identifier.
  - `name`: Account holder name (required).
  - `balance`: Current account balance (system initialized).
  - `created_at`: Account creation timestamp (system generated).
- **ER-ACC-03:** Account `id` must be unique across the system.
- **ER-ACC-04:** Account `name` is required.
- **ER-ACC-05:** Initial account balance must always be 0.
- **ER-ACC-06:** Account `created_at` timestamp must be generated by the system.
- **ER-ACC-07:** The client must not be allowed to set or override the initial balance.

### 3.2 Add Transaction (PDF Page 1 & 2, Section 2)
- **ER-TX-01:** System must provide an API to add a transaction to an account.
- **ER-TX-02:** Each transaction must contain:
  - `id`: Unique transaction identifier.
  - `account_id`: Identifier of the associated account.
  - `type`: Either `credit` or `debit`.
  - `amount`: Transaction amount.
  - `description`: Human-readable description.
  - `reference_id`: Unique reference for the transaction within an account.
  - `created_at`: Transaction creation timestamp generated by the system.
- **ER-TX-03 (Credit Rule):** A credit transaction must increase the account balance by the transaction amount (e.g., balance 100 + credit 50 = 150).
- **ER-TX-04 (Debit Rule):** A debit transaction must decrease the account balance by the transaction amount (e.g., balance 100 - debit 30 = 70).
- **ER-TX-05 (Debit Insufficient Balance Rule):** A debit transaction must be rejected if the account does not have sufficient balance (e.g., balance 100, debit 150 -> rejected, balance remains 100).
- **ER-TX-06 (Duplicate Reference Scope):** For the same account, `reference_id` must be unique.
- **ER-TX-07 (Duplicate Reference Handling):** If a transaction with the same `reference_id` is submitted again for the same account:
  - A new transaction must NOT be created.
  - The account balance must NOT change.
  - The API must return an appropriate response indicating that the transaction already exists (HTTP 409 Conflict with stable code `DUPLICATE_REFERENCE`).
- **ER-TX-08 (Cross-Account Reference Reuse):** The same `reference_id` may be used by different accounts.

### 3.3 Get Account Balance (PDF Page 2, Section 3)
- **ER-BAL-01:** System must provide an API to fetch the current balance of an account.
- **ER-BAL-02:** Response must include at least `account_id` and `balance`.
- **ER-BAL-03:** If the account does not exist, return an appropriate error response (HTTP 404 Not Found).

### 3.4 Get Transaction History (PDF Page 2 & 3, Section 4)
- **ER-HIST-01:** System must provide an API to fetch all transactions for an account.
- **ER-HIST-02 (Filtering):** The API must support filtering by transaction type (`credit` or `debit`). If no type is provided, return both credit and debit transactions.
- **ER-HIST-03 (Pagination):** Support pagination using parameters such as `page` and `limit`.
- **ER-HIST-04 (Pagination Metadata):** The API must return enough information for the client to understand pagination, including:
  - `current page`
  - `page size`
  - `total records`
  - `total pages`
- **ER-HIST-05 (Sorting):** Transactions must be returned in latest-first order, based on `created_at`.

### 3.5 Data Integrity & Immutability (PDF Page 3 & 4, Section 5 & 6)
- **ER-INT-01 (Data Consistency):** The implementation must maintain data consistency at all times.
- **ER-INT-02 (Transaction Immutability):** Once a transaction is created, it must not be editable or deletable through the API. The fields (`type`, `amount`, `description`, `reference_id`, `account_id`, `created_at`) must remain permanently unchanged.
- **ER-INT-03 (Balance Consistency):** The account balance must always represent the mathematical result of all valid transactions for that account (Initial: 0 + $\sum \text{credits} - \sum \text{debits}$).
- **ER-INT-04 (Failed/Rejected Non-impact):** A failed or rejected transaction must not affect the account balance or create ledger entries.
- **ER-INT-05 (Atomicity):** Creating a transaction and updating the account balance must be treated as one atomic operation. If either operation fails, neither change should be persisted.

### 3.6 Validations & Error Handling (PDF Page 4, Section 7 & 8)
- **ER-VAL-01:** Validate all incoming data.
- **ER-VAL-02:** Account name must be provided (non-empty string).
- **ER-VAL-03:** Account ID must exist when creating a transaction.
- **ER-VAL-04:** Transaction type must be strictly `credit` or `debit`.
- **ER-VAL-05:** Amount must be strictly greater than 0.
- **ER-VAL-06:** `reference_id` must be provided (non-empty string).
- **ER-VAL-07:** Duplicate `reference_id` for the same account must be rejected with an appropriate error.
- **ER-VAL-08:** Debit transactions must have sufficient balance.
- **ER-VAL-09:** Invalid account IDs must return an appropriate error (HTTP 404 Not Found for non-existent account; HTTP 422 for malformed identifier syntax).
- **ER-VAL-10:** Invalid request data must return an appropriate validation error (HTTP 422 Unprocessable Entity).
- **ER-ERR-01:** Implement proper HTTP status codes and meaningful, consistent error responses via a unified error envelope.

### 3.7 Bonus: Money Transfer (PDF Page 4 & 5, Section 9)
- **OE-XFER-01:** Provide an API to transfer money from one account to another.
- **OE-XFER-02:** Source account must have sufficient balance.
- **OE-XFER-03:** Both source and destination accounts must exist.
- **OE-XFER-04:** The debit from the source account and credit to the destination account must happen atomically.
- **OE-XFER-05:** If any part of the transfer fails, the entire transfer must be rolled back. A partial transfer must never be possible.

## 4. Engineering Safeguards (Non-Negotiable Architecture Controls)

- **ES-01 (Monetary Representation & Currency):** All balances and amounts must be represented as 64-bit integer minor units (`BIGINT` in PostgreSQL, integer paise for INR, cents for USD) named `balance_minor` and `amount_minor`. Binary floating-point arithmetic is strictly forbidden. 1 INR = 100 paise.
- **ES-02 (Database-Enforced Non-Negative Balance):** The accounts table must feature a database check constraint (`balance_minor >= 0`) ensuring that concurrent debits or edge-case bugs cannot overdraw an account.
- **ES-03 (Pessimistic Concurrency & Row Locking):** To prevent race conditions under concurrent debits, account rows must be locked in PostgreSQL via `SELECT ... FOR UPDATE` within the transaction before performing balance updates.
- **ES-04 (Database-Level Composite Unique Constraint):** Enforce `CONSTRAINT uq_account_reference UNIQUE (account_id, reference_id)` at the database schema level so concurrent duplicate requests cannot insert duplicate transactions.
- **ES-05 (Deadlock-Risk Reduction for Transfers):** When locking multiple accounts in a transfer, lock accounts in a deterministic order (ascending UUID) to substantially reduce deadlock risk. Note: This reduces deadlock risk between transfers, but does not guarantee deadlocks are impossible in all concurrent DB workloads; transaction retry policies remain necessary.
- **ES-06 (Database-Level Immutability Safeguards):** The application database runtime role (`ledger_app`) must not be granted `UPDATE` or `DELETE` permissions on the `transactions` table. An append-only ledger pattern must be enforced at the storage engine level.
- **ES-07 (Deterministic Ordering Secondary Key):** In transaction history, sort by `created_at DESC, id DESC` to guarantee deterministic pagination ordering when multiple transactions share identical timestamps.
- **ES-08 (Resource Protection & Pagination Limits):** Enforce hard upper bounds on pagination `limit` (1 to 100 items; default 20) to prevent denial-of-service and memory exhaustion.
- **ES-09 (Zero Sensitive Data in Logs / Safe Errors):** Sanitize all logs, strip stack traces from client responses, use a unified error envelope, and issue stable machine-readable error codes.
- **ES-10 (Environment Safety & Access Control):** Unauthenticated access is permitted strictly for local evaluation under `ALLOW_UNAUTHENTICATED_ACCESS=true`. In `ENVIRONMENT=production`, the application must fail startup if `ALLOW_UNAUTHENTICATED_ACCESS` is true. An account UUID must never be treated as authorization.
- **ES-11 (Transaction Boundary & Rollback Ownership):** The service layer transaction boundary owns the database session and must explicitly issue `await session.rollback()` on any failure using bare `raise`. Rollback must never be assumed to happen in an outer HTTP exception handler.
- **ES-12 (No Blind Retries on Ambiguous Outcomes):** Connection drops or timeouts during `COMMIT` represent ambiguous outcomes. Blind retries of financial writes are strictly prohibited; clients must reconcile using `reference_id`.

## 6. Analysis of Ambiguities & Distinctions

### 6.1 Duplicate Reference Handling
- **Assessment Requirement (Page 2):** "If a transaction with the same `reference_id` is submitted again for the same account: A new transaction must not be created. The account balance must not change. The API should return an appropriate response indicating that the transaction already exists."
- **Specification:**
  - Return **HTTP 409 Conflict** with stable error code `DUPLICATE_REFERENCE`.
  - **Security Sanitization:** To avoid data leakage across unauthorized callers in unauthenticated or shared environments, the 409 response contains a clean error message and correlation `request_id`, without exposing historical transaction amounts, timestamps, or internal record IDs.

### 6.2 Monetary Representation & Currency Decision
- **Specification:**
  - The public API, internal domain models, and PostgreSQL tables consistently use `amount_minor` and `balance_minor` as 64-bit signed integers (`BIGINT`).
  - Currency is tracked as ISO 4217 code (`INR`), with 1 INR = 100 paise.
  - Floating-point representations (`float`, `double`) are completely prohibited.

### 6.3 Identifier Formats
- **Specification:** RFC 4122 **UUIDv4** strings for all entity IDs.
- **Security Rule:** An account UUID is purely an address/identifier, never a credential or authorization token.

### 6.4 Access Control Scope
- **Specification:** The assessment defines an unauthenticated functional API.
- **Safety Control:** Unauthenticated access is restricted strictly to local evaluation (`ALLOW_UNAUTHENTICATED_ACCESS=true`). In `ENVIRONMENT=production`, the application must refuse startup unless an approved authentication and account-ownership model is enabled.
